# 3. How OpenSpec Carries the Cornerstones

Chapter 1 introduced OpenSpec as one example of a spec-driven way of working, and it named the artifacts of OpenSpec only in passing. Chapter 2 named the principles that those artifacts have to satisfy. This chapter shows how one set of conventions implements those principles. It also shows where the conventions stop.

This chapter is a map, not a manual. One section gives the technical background, for the reader who wants to know what the conventions run on. Installation, commands and configuration belong to the tool's own documentation. What matters here is the shape of the record. Where is intent written down? How is a proposed change kept apart from the system as it is? What keeps the two connected? A different tool could arrange the same material under other names and still serve the same principles. So the question to keep in mind through the chapter is not what the tool does. It is which principle each convention serves.

## 3.1 What the tool consists of

OpenSpec is a small program, not a platform. It is an open-source command-line tool under the MIT license, maintained by Fission-AI and written in TypeScript. It is distributed as an npm package, or as a standalone binary that runs without Node.js. A developer installs it once on a machine and uses it per project. There is no service to sign up for and nothing to host. The OpenSpec project plans its own development with OpenSpec, so its repository is a working example of the conventions this chapter describes.

All of a project's artifacts are Markdown files in the repository. There is no server, no daemon, no database and no API key. Nothing that the work depends on runs between commands. What the project plans and specifies is in Markdown files and nowhere else. The program does keep some state on the machine: the global configuration with its profile, schemas that a user shares across projects, skills installed for every project, and stores registered as standalone OpenSpec repositories. It also sends anonymous usage statistics: the command's name and the release, and nothing of the project. It does not send them if `OPENSPEC_TELEMETRY=0` is set or the configuration turns them off. The `openspec/` tree is plain files, and git versions and shares them like any other file. A session never depends on a service being reachable, because the work uses none. A project that stops using the tool keeps files that any editor can read. The format is Markdown, and the tool operates on it rather than containing it.

The work is split between the agent and the program. The agent in the coding tool drafts and edits the artifacts, because that part needs language and judgment. The program does what should not depend on a model. It parses the Markdown structure, checks the conventions, and counts task checkboxes to compute progress. It also refuses a change that fails validation. At archive, the merge of a delta into the main specifications has two paths. The `openspec archive` command makes the merge in the program. The archive workflow has the agent make the merge, following the rules of the sync workflow, and then validates the main specifications. A later chapter describes both paths. Reporting commands can produce machine-readable output, so the checks can run wherever checks belong. A model writes, a program verifies, and a person approves. A passing validation is a fact about structure, not a verdict on the requirements. The limits from chapter 2 apply unchanged. Structure is exactly the part that a program can be trusted with.

The tool connects to the coding tools through generated files, not through a protocol. The setup command, `openspec init`, writes the skills of OpenSpec into one shared directory, in whatever file format the coding tools expect. From release 2.1, that directory is by default `~/.agents/skills/`, which every project on the machine shares. With `--scope project`, it is the repository's own `.agents/skills/`. The line `skillsScope: project` in the project's configuration then records that choice for everyone who clones the repository. This repository keeps its skills in the project. Each skill but one delivers one workflow, which is OpenSpec's word for one action on a change. The other skill is `openspec`, a router that picks one of the skills for a request. A profile chooses which workflows are installed. From release 2.2, every profile also installs the router. A coding tool reads that directory, either directly or through links of its own. The current release writes no slash commands. The repository's README names the release that this description was checked against. The `openspec update` command generates those files again when the program changes. So the instructions an agent sees stay consistent with the program that checks the agent's work. No protocol stands between the program and the assistant: not an MCP server, and not an API. No assistant is privileged. What the connection moves is text, and text is the one thing that every coding tool already reads.

The shape of a change is data. A schema is a folder of plain files. One YAML file declares each artifact that a change produces: the file it generates, what it requires first, and the instruction the agent receives when it creates the artifact. There is also one Markdown template per artifact. A line in the project's configuration names the schema to use. The default schema produces the four artifacts this chapter describes: proposal, delta specifications, design and tasks. A project can fork a schema and edit it. It can drop an artifact, add one, or rewrite the instructions. The program then enforces the project's schema as if the schema had been shipped that way. The dependencies between artifacts are enablers, not phase gates. They say what becomes possible, not what must happen next. The project decides what a change folder contains, not the tool, and the tool checks whatever the project declared.

The nature of the tool is now stated: a program over plain Markdown versioned by git, which checks what agents write. What remains to describe is what those files hold.

## 3.2 The two parts of the record

The design is easier to remember when it is reduced to two locations in the repository. One set of specifications describes the system as it is today. A separate set of change folders describes work that is proposed or in progress. Both are in a directory called `openspec/`, next to the code they describe.

Everything else in this chapter follows from that split. If the specifications described only the work in progress, the project would have plans and no memory. If they described only the current system, a change would have no place to say what it intends. Because both are kept in one repository, a reader can ask two separate questions. What does this system do? And what is about to change?

## 3.3 The system as it is

The specifications under `openspec/specs/` are organised by capability. A capability is a coherent area of behaviour, and each capability holds requirements and scenarios. A requirement states what must be true of the system. A scenario gives one concrete case that shows the requirement being met or missed.

This makes the cornerstone of current-state knowledge concrete. A developer or an agent who needs to know how the system behaves can read the capability. They do not have to reconstruct the behaviour from code, diagrams or memory. The specification is not a summary of the code, and it is not a design document. It states the behaviour that the code is supposed to have. For that reason, it can be used to judge the code, and not merely to describe it. That is what the convention asks for, but it is not what most repositories contain. Most specifications written this way carry implementation detail, and the detail is there because it helps the agent that reads it. The rule protects the part that has to outlive the code. That is the cornerstone of the specification as shared reference.

## 3.4 A change as a folder

A proposed modification is in `openspec/changes/<change-name>/`. The folder is self-contained. It holds the proposal, which explains why the work is needed, and the delta specifications, which state what changes. It also holds the design, which explains the approach, and the tasks, which break the work into steps. Chapter 1 named these artifacts. The point here is that they are in one place.

That grouping is the cornerstone of a change as a first-class unit, and it is also the cornerstone of reviewability. A reviewer can read the intent, the expected behaviour and the plan before any code exists. The reviewer does not have to reconstruct them from a diff. The grouping also makes a change a unit of work rather than a side effect of version control. A change can be reviewed, revised or abandoned without leaving a half-finished branch behind.

Chapter 1 used the request "add CSV export" to show how much a single sentence leaves undecided. The same request shows what a change folder has to hold. As a change, it becomes `add-csv-export/`. The folder has to answer the questions that the sentence left open: which records are exported, which columns, whether the current filter applies, how dates and numbers are formatted, and who is permitted to export what. The illustration is the one that chapter 1 used, not a change in this repository. Its value is that the request is small enough to remember while the conventions are introduced.

A delta specification does not repeat the whole system specification. It states only what the change does to that specification, using explicit operations: a requirement can be added, modified, removed or renamed. OpenSpec names the four operations ADDED, MODIFIED, REMOVED and RENAMED. So the kind of change is part of the record, and a reader does not have to infer it. The CSV export change adds a requirement that describes export. It may also modify a requirement about who may see which records, because exporting is one way of seeing them. The change leaves the rest of the capability alone.

As a result, the effect of a change on behaviour is visible in one place. A reviewer sees both the new behaviour and its effect on existing behaviour. The reviewer does not have to hold two versions of the whole specification side by side. This is the cornerstone of separation of current and proposed state, expressed as an operation rather than as advice about where to write things. The same record names what the change leaves alone. An exclusion that is written down is a decision, not a gap that a later reader has to guess at.

## 3.5 The rules that apply to all work

The repository also holds the rules that apply to every change: how the project is structured, which standards apply, and what must not break. These rules are in the instruction files that an agent reads when a session opens. One of them is `AGENTS.md`, which is also the one such file that several coding tools read. The rules are also in the project context that the tool loads before planning. Because those rules are kept with the code, the same material is available to a developer, a reviewer and an agent.

That is the cornerstone of shared project context. It does not mean that an agent reads the rules automatically. It means that the rules have a place where they can be found. It also means that a session which consults them starts from the project's conventions, and not from a generic default.

## 3.6 From intent to a merged specification

The artifacts form a path. The proposal says why the work is needed. This is explicit intent, written down before anything is built. The delta says what behaviour changes. The design says how the work will be approached. The tasks connect the design to implementation steps. Each artifact can be checked against the one before it. So a disagreement between intent and plan becomes visible before it becomes a disagreement between plan and code.

That path is the cornerstone of traceability, and it is short on purpose. A change does not have to fill every artifact to be traceable. But it has to be possible to follow the reasoning from the request to the code, without guessing which decision came from where.

A requirement is identified by its own title. The identifier goes with design decisions and tasks, and the specification holds the wording. Everything else points to the requirement. A chapter or an artifact that discusses what the requirement says uses the name, and leaves the sentence where it is. When the wording is copied along, a second copy of a rule appears in a document that is edited on a different schedule. Two copies of one rule can disagree.

Validation is the check at the end of the path. That check is the cornerstone of validation. Acceptance criteria and tests decide whether the implementation satisfies the specification. The specification is the reference for that decision, and the implementation is not its own judge. This is what stops a written record from becoming a description written after the fact. If the code decides what counts as correct, the specification records the outcome of the work. If the specification decides, the work can fail to meet it, and the failure is visible.

Completion keeps the record alive. When the work is finished, the delta is merged into the capability's specification, so the description of the system matches the system again. The change folder then moves into a dated archive. There it keeps the record of what changed and the design that went with it.

That is the cornerstone of living documentation. It is the difference between a specification written before coding and one that is maintained. The current specification is updated because the work changed, not because someone remembered to update it. The archive is not a backup. It is the record of how the current description reached its form. The reasoning in it is only as complete as the people who wrote the change made it. A decision that was settled in a conversation and never written into the change is not in the archive, and nothing later can recover it.

## 3.7 What the conventions leave to people

None of this decides what to build. The conventions give intent a place, a shape and a check, but they do not supply the intent. A change folder can hold a proposal that argues for the wrong feature. It can hold a delta that specifies the wrong behaviour, and tasks that implement it carefully. The record does not prevent that. It makes the decision visible, and that allows someone to challenge the decision before it is built.

That is the last cornerstone, human control, and it is the one that the conventions cannot carry. A tool can hold a decision. It cannot make one.

Validation happens at the end of the change, and nothing checks afterwards whether the specification and the code still agree. A later change can satisfy its own requirement and pass its own tests. It can still break a constraint from an earlier change without anyone noticing. No tool in the sample was shown to look for that. The practitioners who wanted such a check had to build checks of their own. A check would show a disagreement, but not which of the two is wrong.

Most people who work this way read a specification in part rather than in full, or pass the review to another agent. Partial reading is partly what the record is for. The problem, the decisions and the acceptance criteria carry the intent, and the rest is context for whoever implements. Passing the review to another agent is the risk, because it removes the one point at which a person decides what the system should do. The record does not help there either. It shows the path that was taken, and a rejected alternative survives only if someone wrote it down.

The conventions are worth reading as answers to the cornerstones, not as a directory layout. Ten of the eleven cornerstones have a convention in this chapter that carries them, and human control is the limit named above. The split between what the system is and what is about to change carries most of the principles. The rest are carried by where the material is kept, by the path from proposal to tasks, and by the fact that the work is checked against the specification rather than the code. The next chapter follows one requirement through this path, from a sentence that looks complete to the constraint that settles it.
